Policy 1: Account Access and Authentication Policy

1. Policy Identity and Purpose

TitleAccount Access and Authentication Policy
Version1.0
Proposed EffectivityUpon deployment of the system to Barangay 179
Policy OwnerSystem Administrator (Deputy Officer)
Approving RoleBarangay Captain / Deputy Officer
Security ObjectiveEnsure only authorized barangay personnel can access the system through strong authentication practices and proper account management.

2. Scope and Context

System: Barangay 179 Crime CART desktop application (Electron + Express.js + MySQL).

Users: Deputy Officer (admin), Team Leader, Kagawad (view-only), Tanod (self-service).

Activities Covered: Account creation, login/logout, password management, session handling.

Exclusions: Physical access to the workstation running the app is governed by barangay office procedures, not this policy. Network-based attacks are out of scope since the app runs on localhost only.

3. Risk Basis

RiskAssetThreatWeaknessConsequenceCurrent SafeguardLikelihoodImpactPriority
R1: Unauthorized admin access via demo credentials User accounts, crime data Insider or anyone who views login.js source code Hardcoded demo credentials (admin/admin123) in frontend code and schema.sql Full admin access to all crime records, user management, and system settings None — credentials are openly visible High High Critical
R2: Brute-force password guessing User accounts Attacker with access to the login page Weak or default passwords; no server-side complexity requirements Account takeover, unauthorized data access Login lockout (5 attempts/15 min) + rate limiter (8 req/5 min) Medium High High
R3: Session hijacking from exposed tokens Active user sessions Shoulder surfing or console inspection Session token and user role logged to browser console; user data duplicated in localStorage Impersonation of logged-in user Token stored in sessionStorage (cleared on tab close); 30-min idle timeout Low Medium Medium

Rating Justification: R1 is Critical because the credentials are plainly visible in the source code, requiring zero skill to exploit and granting full admin access. R2 is High because the lockout mechanism exists but weak passwords are still allowed by the system. R3 is Low likelihood since it requires physical access to the machine, but Medium impact because a stolen token grants full session access until timeout.

4. Policy Clauses

  1. PC-1.1: The Deputy Officer must remove all hardcoded demo credentials from frontend source code (login.js) and database seed scripts (schema.sql) before the system goes live.
  2. PC-1.2: All user passwords must be at least 8 characters and contain at least one uppercase letter, one number, and one special character. The server must enforce this via Joi validation on all password creation and change endpoints.
  3. PC-1.3: The Deputy Officer must create unique accounts for each user. Sharing of accounts between barangay personnel is prohibited.
  4. PC-1.4: The Remember Me checkbox must be removed from the login page. Sessions must rely solely on sessionStorage tokens that are cleared when the browser tab is closed.
  5. PC-1.5: All console.log statements that output user credentials, session tokens, or user roles must be removed from both frontend (login.js) and backend (server.js) code before deployment.
  6. PC-1.6: The Deputy Officer must deactivate accounts of personnel who are no longer assigned to Barangay 179 within 3 business days of their departure.
  7. PC-1.7: The localStorage duplication of user data (login.js) must be removed. Session data must only be stored in sessionStorage.

5. Roles and Enforcement

FunctionResponsibleDetails
ApprovalBarangay CaptainApproves the policy and any exceptions to password rules.
ImplementationDevelopment Team / Deputy OfficerRemoves demo credentials, implements password complexity, removes console logs. Deputy Officer manages user accounts.
CommunicationDeputy OfficerBriefs all users on password requirements and no-sharing rule during onboarding.
MonitoringDeputy OfficerReviews audit logs weekly for suspicious login patterns (multiple failed attempts, logins outside office hours).
Violation ReviewBarangay Captain + Deputy OfficerViolations are handled through existing barangay personnel disciplinary procedures. Accounts are suspended pending review.

Policy 2: Data Handling and Privacy Policy

1. Policy Identity and Purpose

TitleData Handling and Privacy Policy
Version1.0
Proposed EffectivityUpon deployment of the system to Barangay 179
Policy OwnerDeputy Officer (System Administrator)
Approving RoleBarangay Captain
Security ObjectiveProtect the confidentiality and integrity of crime records, personal information of residents, and system credentials stored in the database.

2. Scope and Context

System: MySQL database (brgydata) containing incident records, blotter entries, user accounts, tanod information, patrol schedules/logs, and CART analytics data.

Users: All system roles that interact with crime data and personal information.

Activities Covered: Data entry, viewing, editing, archiving, exporting, and database administration.

Exclusions: Physical paper records maintained by the barangay are outside this policy's scope. Data shared with external agencies (PNP) follows their own handling procedures.

3. Risk Basis

RiskAssetThreatWeaknessConsequenceCurrent SafeguardLikelihoodImpactPriority
R1: Full database compromise via root access All database tables SQL injection (if introduced) or app-level vulnerability Application connects as MySQL root user with DROP, GRANT, and FILE privileges Attacker could drop all tables, export the entire DB, or escalate privileges Parameterized queries prevent SQL injection currently Medium High Critical
R2: Credential exposure from .env file Database password, app secrets File system access, accidental git commit DB password stored in plaintext in .env; file was modified and may exist in git history Direct database access bypassing the application entirely .env listed in .gitignore Medium High High
R3: Sensitive data leaked through API responses Password hashes, PIN codes, personal information API consumer or browser inspection Potential for new endpoints to accidentally include sensitive fields Exposure of hashed credentials or personal data TANOD_PUBLIC_COLUMNS excludes pin_code_hash; user queries omit password_hash Low Medium Medium

Rating Justification: R1 is Critical because root DB access means any future vulnerability could escalate to total data loss, even though parameterized queries currently block injection. R2 is High because a plaintext password in a file is one misconfigured backup away from exposure. R3 is Low likelihood due to existing field exclusions, but the pattern must be maintained as new endpoints are added.

4. Policy Clauses

  1. PC-2.1: The development team must create a dedicated MySQL user (e.g., brgyapp) with only SELECT, INSERT, UPDATE, and DELETE privileges on the brgydata database. The root account must not be used by the application.
  2. PC-2.2: The database password must be rotated before deployment. If the password exists in git history, the history must be scrubbed using git filter-repo or the repository must be recreated.
  3. PC-2.3: All new API endpoints must exclude sensitive fields (password_hash, pin_code_hash) from responses. Code reviews must verify this before merging.
  4. PC-2.4: Crime incident records containing victim or complainant names must only be accessible to Deputy Officer and Team Leader roles. Kagawad sees aggregated analytics only.
  5. PC-2.5: Soft-deleted (archived) records must be retained for a minimum of 1 year for legal and audit purposes. Permanent deletion requires Deputy Officer approval and must be logged in the audit trail.
  6. PC-2.6: No system user may export or copy crime data to personal devices or external storage without written authorization from the Barangay Captain.

5. Roles and Enforcement

FunctionResponsibleDetails
ApprovalBarangay CaptainApproves data handling procedures and any data export requests.
ImplementationDevelopment TeamCreates least-privilege DB user, rotates credentials, verifies API field exclusions.
CommunicationDeputy OfficerEnsures all users understand data sensitivity and the no-export rule.
MonitoringDeputy OfficerReviews audit logs for unusual data access patterns (bulk reads, off-hours access).
Violation ReviewBarangay CaptainUnauthorized data export or sharing is referred to the Barangay Captain for action under existing personnel procedures.

Policy 3: Audit Logging and Monitoring Policy

1. Policy Identity and Purpose

TitleAudit Logging and Monitoring Policy
Version1.0
Proposed EffectivityUpon deployment of the system to Barangay 179
Policy OwnerDeputy Officer (System Administrator)
Approving RoleBarangay Captain
Security ObjectiveMaintain a reliable, tamper-resistant record of all security-relevant actions to support incident investigation, accountability, and compliance.

2. Scope and Context

System: audit_logs and tanod_audit_logs tables, login_attempts table, and server-side logging in server.js.

Users: All system users generate log entries. Only the Deputy Officer can view them.

Activities Covered: Login/logout events, failed authentication attempts, CRUD operations on all entities, settings changes, password resets.

Exclusions: Application performance metrics and server health monitoring are outside this policy. Physical access logs to the barangay office are managed separately.

3. Risk Basis

RiskAssetThreatWeaknessConsequenceCurrent SafeguardLikelihoodImpactPriority
R1: Audit log tampering audit_logs table Malicious admin or compromised app App connects as root (can DELETE/UPDATE audit_logs); no log integrity verification Evidence of unauthorized actions erased, hindering investigation No DELETE/UPDATE API endpoints for logs (append-only at app layer) Medium High High
R2: Insufficient log detail Audit trail completeness Incomplete logging in new features New endpoints might not call logAudit() Gaps in accountability — actions occur without a record Existing logAudit() covers all current CRUD + auth events Medium Medium Medium
R3: Log data accumulation without retention policy Database storage, system performance Unbounded log growth over years of operation No log retention or archiving mechanism Database bloat, slower queries, potential storage exhaustion None Medium Low Medium

Rating Justification: R1 is High because the root DB user (see Policy 2) can bypass the app-layer append-only restriction. Once #14 is fixed with a least-privilege user, log tampering risk drops to Low. R2 is Medium because the current codebase has good coverage but any future feature additions could create gaps. R3 is Medium because while not an immediate threat, years of operation will accumulate significant data.

4. Policy Clauses

  1. PC-3.1: Every new API endpoint that creates, updates, or deletes any record must include a call to logAudit() or logTanodAudit() with the appropriate action, entity type, and old/new data. Code reviews must verify this.
  2. PC-3.2: The dedicated database user (per Policy 2, PC-2.1) must not have DELETE or UPDATE privileges on the audit_logs and tanod_audit_logs tables, ensuring logs are tamper-proof at the database level.
  3. PC-3.3: The Deputy Officer must review audit logs at least once per week, checking for: failed login spikes, off-hours access, bulk data operations, and unauthorized role escalation attempts.
  4. PC-3.4: Audit log entries must not contain sensitive data such as plaintext passwords, session tokens, or PIN codes. The logAudit() function must strip these fields from old_data and new_data before insertion.
  5. PC-3.5: Audit logs older than 3 years must be exported to a separate archive file and may then be purged from the active database. The archive must be stored securely alongside database backups.
  6. PC-3.6: Any anomalies found during log review (e.g., multiple failed logins from one account, record deletions outside normal hours) must be reported to the Barangay Captain within 24 hours.

5. Roles and Enforcement

FunctionResponsibleDetails
ApprovalBarangay CaptainApproves log retention periods and archive schedule.
ImplementationDevelopment TeamRestricts DB user privileges on audit tables, ensures logAudit() on all endpoints, builds archive/purge script.
CommunicationDeputy OfficerInforms users that all actions are logged and subject to review.
MonitoringDeputy OfficerConducts weekly log reviews and documents findings.
Violation ReviewBarangay Captain + Deputy OfficerAnomalies and potential violations are investigated using the audit trail. Findings follow existing barangay disciplinary processes.

Policy 4: Backup and Recovery Policy

1. Policy Identity and Purpose

TitleBackup and Recovery Policy
Version1.0
Proposed EffectivityUpon deployment of the system to Barangay 179
Policy OwnerDeputy Officer (System Administrator)
Approving RoleBarangay Captain
Security ObjectiveEnsure crime records and system data can be recovered in the event of hardware failure, data corruption, accidental deletion, or other disasters.

2. Scope and Context

System: MySQL database (brgydata), uploaded files (evidence photos/videos), application configuration (.env, config.json).

Users: Deputy Officer is the sole authorized person for backup and restore operations.

Activities Covered: Scheduled database backups, encrypted storage, restore procedures, and backup verification testing.

Exclusions: Physical hardware maintenance (e.g., hard drive replacement) follows barangay IT procurement procedures. Backups of the operating system or Electron runtime are not covered.

3. Risk Basis

RiskAssetThreatWeaknessConsequenceCurrent SafeguardLikelihoodImpactPriority
R1: Data loss from hardware failure Entire brgydata database Hard drive failure, power surge Backups are manual only (npm run backup); no automated schedule Loss of all crime records, user accounts, analytics data since last manual backup Manual backup script with 14-file retention Medium High High
R2: Backup theft exposing sensitive data Backup SQL files Unauthorized file access, stolen USB drive Backup files are plain-text SQL containing all records including personal data Exposure of all crime records, victim info, and password hashes None — files are unencrypted Medium High High
R3: Untested restore process fails when needed Disaster recovery capability Corrupted backup, incompatible schema version No restore script or documented procedure; never tested Inability to recover data even though backups exist None Medium High High

Rating Justification: All three risks are High because backups are the last line of defense against data loss. A backup system that is manual, unencrypted, and untested provides only the illusion of protection. In a law enforcement context, losing crime records could compromise active cases.

4. Policy Clauses

  1. PC-4.1: Database backups must run automatically at least once daily. The development team must implement a scheduled backup using node-cron or the OS task scheduler.
  2. PC-4.2: All backup files must be encrypted before storage using AES-256 or GPG encryption. Unencrypted SQL dumps must not be retained on disk.
  3. PC-4.3: The Deputy Officer must copy the latest encrypted backup to a separate USB drive or external storage at least once per week and store it in a locked location separate from the workstation.
  4. PC-4.4: A documented restore procedure must be created and tested. The development team must provide a restore script that the Deputy Officer can run to recover from a backup.
  5. PC-4.5: The Deputy Officer must perform a test restore on a separate database at least once per quarter to verify backup integrity. The test date and result must be documented.
  6. PC-4.6: Backup files must be retained for a minimum of 30 days (rolling). The current 14-file retention policy must be adjusted if daily backups produce fewer than 30 days of coverage.
  7. PC-4.7: Uploaded evidence files (photos/videos in the uploads/ directory) must be included in the backup procedure, not just the database.

5. Roles and Enforcement

FunctionResponsibleDetails
ApprovalBarangay CaptainApproves backup schedule, retention period, and off-site storage location.
ImplementationDevelopment TeamImplements automated scheduling, encryption, and restore script.
CommunicationDeputy OfficerKnows how to initiate manual backup and restore in an emergency.
MonitoringDeputy OfficerChecks daily that the automated backup ran (verifies latest file timestamp). Performs quarterly restore test.
Violation ReviewBarangay Captain + Deputy OfficerIf a backup is missed for more than 48 hours, the Deputy Officer must investigate and resolve within 24 hours. Chronic failures are escalated to the Captain.

Policy 5: Acceptable Use and Operational Security Policy

1. Policy Identity and Purpose

TitleAcceptable Use and Operational Security Policy
Version1.0
Proposed EffectivityUpon deployment of the system to Barangay 179
Policy OwnerDeputy Officer (System Administrator)
Approving RoleBarangay Captain
Security ObjectiveDefine proper use of the system, protect the operational environment from misconfiguration and accidental exposure, and ensure the system remains available for its intended purpose.

2. Scope and Context

System: The entire Crime CART application — Electron shell, Express backend, MySQL database, and the workstation it runs on.

Users: All barangay personnel who use or administer the system.

Activities Covered: Day-to-day system use, software updates, workstation management, network configuration, and handling of system output (reports, heatmaps, patrol routes).

Assumptions: The system operates as a standalone desktop application on a single barangay workstation. If the deployment model changes to a networked or cloud environment, this policy must be revised.

3. Risk Basis

RiskAssetThreatWeaknessConsequenceCurrent SafeguardLikelihoodImpactPriority
R1: System unavailable due to broken dependencies Application availability Internet outage or CDN takedown Frontend loads 10+ external CDN resources (fonts, icons, Chart.js, Leaflet, Mapbox, etc.) App UI breaks completely without internet — unusable for field operations Core logic runs locally; only UI assets are external High High Critical
R2: Debug information leaking to users System internals, security posture Curious user opening browser DevTools 92 console.log statements in server.js; login.js logs user role and name; route listing on startup Internal system details exposed, aiding potential abuse Electron DevTools can be disabled in production Low Low Low
R3: Misuse of system for unauthorized purposes Crime data integrity, system reputation Barangay personnel using the system outside its intended purpose No acceptable use guidelines communicated to users Fabricated records, privacy violations, unauthorized data sharing Role-based access limits what each user can do; audit logging tracks actions Low High Medium

Rating Justification: R1 is Critical because as a law enforcement tool, the system must work reliably even without internet — tanods in the field can't wait for a CDN. R2 is Low because it requires opening DevTools, which most users won't do, and the information is mostly operational, not directly exploitable. R3 is Low likelihood due to existing RBAC and audit trail, but High impact because fabricated crime records could have legal consequences.

4. Policy Clauses

  1. PC-5.1: The development team must bundle all external CDN dependencies (Google Fonts, Font Awesome, Chart.js, Bootstrap, Leaflet, Mapbox GL JS, Turf.js) locally within the application before deployment. The app must function fully without internet.
  2. PC-5.2: The system must only be used for its intended purpose: recording crime incidents, generating heatmaps, CART analysis, and managing tanod patrols for Barangay 179. Using the system to create false records is prohibited.
  3. PC-5.3: Printed reports, patrol routes, and heatmaps containing crime data must be treated as confidential. They must not be left unattended, photographed, or shared on social media.
  4. PC-5.4: The development team must remove or disable all unnecessary console.log statements in production builds. Server startup must not print route listings or internal configuration details.
  5. PC-5.5: The workstation running the system must have a screen lock with a password. If a user steps away, they must lock the screen or log out of the application.
  6. PC-5.6: The Deputy Officer must not install unrelated software on the system workstation that could introduce malware or conflict with the application. Software changes require prior approval.
  7. PC-5.7: If the system needs to be connected to a network (e.g., for updates or data sharing), TLS/HTTPS must be configured first. The current HTTP-only configuration is acceptable only for localhost desktop use.

5. Roles and Enforcement

FunctionResponsibleDetails
ApprovalBarangay CaptainApproves acceptable use rules and any exceptions (e.g., temporary internet connection for updates).
ImplementationDevelopment Team / Deputy OfficerDev team bundles dependencies and removes debug output. Deputy Officer configures workstation security (screen lock, no unauthorized software).
CommunicationDeputy OfficerAll users are briefed on acceptable use rules before being given system access. A printed summary is posted near the workstation.
MonitoringDeputy OfficerPeriodic spot checks that the workstation is locked when unattended. Audit log review for unusual activity.
Violation ReviewBarangay CaptainViolations (false records, unauthorized sharing, unattended unlocked workstation) are handled through existing barangay personnel procedures.
